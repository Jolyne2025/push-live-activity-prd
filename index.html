1. 背景与目标

1.1 背景

  • 行业趋势：iOS Live Activity（灵动岛实时活动）自 iOS 16.1 推出以来，已成为高意图的持续互动界面。相比一次性推送通知，Live Activity 在灵动岛/锁屏持续显示 8-12 小时，用单一持久界面替代多条推送，缓解通知疲劳（美国用户日均收 46 条推送）并提升可见性。
  • 用户价值：B2B 买家在"发出询盘 → 等待卖家回复"过程中存在高频查看需求，Live Activity 可将"等待状态"可视化，减少焦虑、提升回访。
  • iPhone 18 事件：iPhone 18 Pro 灵动岛物理尺寸将缩小 ~35%（20.7mm → 13.5mm），Apple 保持 point 值不变（compact 250pt/230pt），标准 Live Activity 自动适配，不构成阻塞。
  • Visable 现状：iOS Push 仅支持纯文本/系统默认样式，无富媒体、无 Live Activity 能力；当前系统消息类策略（MESSAGE_SENT + UNANSWERED）是 Push AB 的核心来源（60.5%），但依赖重复推送维持可见性。

1.2 目标

目标内容成功指标（一期）
G1: 提升转化 通过 Live Activity 提升系统消息类场景的打开率与 AB 贡献 消息类 open rate 提升 ≥20%（相对）；增量 AB ≥ +2.0/天（中性假设）
G2: 降低疲劳 用持续状态界面替代同场景重复推送，减少推送量 消息类推送量下降 ≥20% 且打开率不降；退订率不上升
G3: 能力沉淀 沉淀 iOS Live Activity 技术能力，为后续场景扩展（订单/物流跟踪等）铺路 技术方案可复用、埋点体系完整
⚠️ 关键边界（Apple 红线）：Apple 明确禁止 Live Activity 用于促销、优惠、营销活动或广告，且必须由用户主动操作触发。因此本需求一期仅覆盖系统通知/交易状态跟踪类场景，营销类策略（RECOMMENDATION/RFQ_marketing/TRENDING）不纳入 Live Activity 范围。

3. 业务收益测算

3.1 收益逻辑

增量 AB = iOS 可触达 open_uv × 打开率相对提升 × open→AB 转化率
其中 iOS 可触达 open_uv = 场景 open_uv × iOS 用户占比 × Live Activity 支持率（iOS 16.1+，≈100% 近年设备）
  • 打开率提升来源：灵动岛/锁屏常驻显示 8h（比一次性通知曝光时长提升 10 倍+），用户无需进入通知中心即可看到并点击；等待场景用户有高频查看动机。
  • 行业佐证：Pushwoosh 2025 基准电商 iOS CTR 3.05%（营销类），而 Visable 系统消息 open rate 已达 34%（消息类天然高）；Live Activity 场景（如配送）用户注意力显著高于一次性通知。
  • 推送量下降收益：同一会话内以 Live Activity 替代重复推送（如 UNANSWERED 的多轮提醒），降低推送总量 → 降低退订风险（定性收益，见 G2）。

4. 业务需求定义与业务规则

4.1 需求总述

在 iOS 16.1+ 设备上，为消息/询盘状态跟踪类系统通知提供 Live Activity（灵动岛实时活动）展示：当用户处于"等待卖家回复"状态时，灵动岛与锁屏持续展示状态卡片，状态变化实时更新，点击卡片进入 App 对应会话页。同一会话不再重复推送多轮提醒，以持续状态界面替代。

4.2 一期业务场景

场景触发条件（用户主动行为）Live Activity 展示内容替代的现有推送
S1: 询盘等待回复
P0		 买家发出询盘（Contact Supplier / RFQ 提交）后，进入等待卖家回复状态 灵动岛：询盘图标 + "等待回复"状态；锁屏扩展态：询盘摘要（产品名）、已等待时长、卖家人数 替代 UNANSWERED_REMINDER 的重复提醒推送
S2: 新消息待查看
P0		 收到卖家新消息（会话中） 灵动岛：消息图标 + "N 条新消息"（不展示消息内容，规避敏感数据限制）；锁屏：消息发送者名称 + 摘要提示（可配置） 替代 MESSAGE_SENT 的重复推送
S3: 多会话聚合
P1		 同时有多个未回复会话（并发 ≤5 个） 极简式：单图标 + 汇总数量 "3 个待回复"；点击进入消息列表页 减少多会话场景的推送轰炸

4.3 业务规则

规则 R1: 场景边界（红线）

  • Live Activity 仅限系统通知/交易状态类场景；营销类（推品/促销/权益）一律不使用 Live Activity（Apple App Review 红线）。
  • 非用户主动触发的事件（如纯系统广播）不得启动 Live Activity。

规则 R2: 授权与权限

  • iOS 17+：用户已开启 Push 通知时，Live Activity 默认随之开启（系统行为），无需额外弹窗；用户可在系统设置中单独关闭。
  • iOS 16.x：首次启动 Live Activity 时系统弹窗单独授权（"允许实时活动？"）。
  • 退订关系：跟随现有 Push 退订体系——用户退订 Push 后不再启动 Live Activity；已启动的即时结束。

规则 R3: 生命周期

触发（用户主动行为）→ 启动 LA（灵动岛 compact + 锁屏）→ 状态更新（回复到达 / 等待超时 / 多消息聚合）→ 结束（任务完成 / 用户关闭 / 超时 8h）
节点条件动作
启动买家发出询盘 / 收到第一条新消息创建 Live Activity（ActivityKit start），携带会话 ID、产品信息（S1）/消息数（S2）
更新① 收到新回复（状态未终结）② 等待时长跨越阈值（如 6h/24h）③ 新消息累计推送更新（APNs push-to-update 或 App 内 update），刷新状态文案
结束① 卖家已回复且用户已查看 ② 用户手动关闭 ③ 超过 8h（灵动岛）/ 12h（锁屏）系统自动收起结束活动（end），同时发送一条收尾推送（如"卖家回复了你的询盘"）引导回访

规则 R4: 与现有推送的关系（替代而非叠加）

  • 同一会话处于 Live Activity 活跃期间，不重复发送同场景的普通推送（MESSAGE_SENT / UNANSWERED_REMINDER 跳过）；状态变化由 Live Activity 更新承载。
  • Live Activity 结束时发一条收尾推送（通知内容可含按钮/富文本，不受 LA 限制）。
  • 预期效果：消息类推送量下降（G2），打开率提升（G1）。

规则 R5: 疲劳度与频控

  • 沿用现有 Push 疲劳度体系：Live Activity 的启动/更新计入同一会话的触达频次；单用户并发 Live Activity ≤5 个（系统上限）。
  • 同一用户 24h 内启动 Live Activity 上限：待定（建议 ≤3 次，与现有消息类频控对齐）。

规则 R6: 敏感数据合规

  • 灵动岛/锁屏不展示消息正文内容（Apple 敏感数据限制），仅展示状态、数量、发送者名称。
  • 询盘内容摘要（产品名/规格）仅展示在锁屏扩展态，且长度 ≤2 行。

规则 R7: 双端一致性

  • iOS 走 Live Activity；Android 维持现有推送（无灵动岛能力），但节奏对齐：Android 在 LA 结束点（收尾推送）同步收到推送。
  • 两端文案共用模板体系（沿用现有策略表配置），减少维护成本。

4.4 非功能需求

类别要求
兼容性iOS 16.1+；iPhone 18 新灵动岛（iOS 27）自动适配；iOS 27 横屏使用 isDynamicIslandLimitedInWidth 提供替代视图
性能LA 更新延迟 ≤30s（服务端事件 → 设备渲染）；更新频率遵循 iOS 18 限制（5-15s 刷新周期）

5. 技术方案与分工

5.1 技术架构总览

[业务事件源: 会话/询盘/消息状态] → [服务端 LA 状态服务] → [APNs push-to-start/update] → [wlw-mobile-app: ActivityKit + WidgetKit 渲染] → [灵动岛/锁屏展示] → [点击深链回 App]
  • 推送通道：APNs（Live Activity 专用 token，与 FCM 普通推送并行）；FCM 继续承载普通推送与收尾推送。
  • 启动方式：App 内 ActivityKit 启动（S1/S2 触发时 App 处于活跃/前台）；iOS 17.2+ 支持 Push-to-Start（作为增强项 P1）。

5.3 App 前端技术要点（陈峰）

  • ActivityAttributes / ContentState：静态数据（会话 ID、产品信息）与动态数据（消息数、等待时长）分离，支持 staleDate 过期展示。
  • 三态视图：compact（灵动岛左/右端）+ minimal（多活动折叠）+ expanded（长按展开）+ 锁屏横幅；使用 ContainerRelativeShape 匹配圆角。
  • iOS 27 横屏：isDynamicIslandLimitedInWidth 环境值判断，提供替代紧凑视图（如仅图标）。
  • 更新方式：优先 push-to-update（APNs），App 活跃时可用 App 内 update 兜底。
  • 并发管理：单用户 ≤5 个活动，超出时按"最旧优先"结束或聚合为 S3 汇总卡。

5.4 App 后端技术要点（杨焱 · V技术）

  • LA token 管理：客户端启动 LA 后上报 pushToken → 服务端存储并绑定会话；与 FCM token 分开管理。
  • 事件驱动更新：会话服务/消息服务的事件流 → LA 状态服务 → APNs 下发（push-type: liveactivity）。
  • 生命周期指令：start/update/end 三类指令 + 幂等控制（同一会话多次事件合并）。
  • 降级策略：APNs 失败/超时 → 回落到现有普通推送（保证触达不丢）。

5.5 技术前置确认项

  1. wlw-mobile-app 是否已集成 ActivityKit？iOS 最低支持版本？（陈峰）
  2. iOS Notification Service Extension 是否存在？（决定是否可做富媒体/按钮收尾推送）（陈峰）
  3. 现有 FCM 链路是否已支持 APNs 旁路（或需要新建 APNs 通道）？（杨焱）
  4. 会话/询盘事件流是否已存在于现有后端架构？（决定 LA 状态服务的接入成本）（杨焱）

6.2 归因与口径

  • LA 事件与 by-push-id 关联：LA 启动时继承触发会话的 strategy_id（如 UNANSWERED），tap 后深链携带 push_id/strategy_id/landing_page_id，下游 session 归因沿用现有 session-based 归因。
  • 漏斗口径：LA 启动率 → LA tap-through → App 打开 UV → AB/AB2（沿用 active_buyers.channel='push'）。
  • 新增看板指标：LA 启动率、分展示面 tap-through 率、LA 打开 UV 增量、LA 归因 AB/AB2、推送量下降幅度（替代验证）。

止损规则退订率相对提升 >10% 或 open rate 下降 >5% → 提前终止，回落现有策略

7.2 成功指标（Go/No-Go 门槛）

一期上线（实验通过）条件：① 消息类 open rate 相对提升 ≥20% 且统计显著（p<0.05）；② 消息类 AB 增量 ≥ +1.5/天；③ 退订率无显著上升。
二期扩展条件：一期通过后，将 S3 多会话聚合、iOS 17.2 Push-to-Start、更多状态场景（订单/物流，如产品线存在）纳入二期。
